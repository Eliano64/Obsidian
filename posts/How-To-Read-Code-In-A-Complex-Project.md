# 建立框架

读代码是为了弄清这段代码在做什么：在什么输入下进入哪条分支，从哪个分支返回什么。要改动，先得把这件事弄清；改完还要拿这份理解再核对一遍。

框架指两件事：模块的边界，以及数据从哪进来、从哪出去。先有框架，才能判断某一段代码要不要读。

边界的假设从文档取，假设对不对要回到代码里确认。文档说明作者打算怎么分，代码说明实际怎么分。只读文档会把意图当现状；只读代码，则要重新推一遍作者的划分。

| 来源 | 能提供的信息 | 需要回到代码确认的部分 |
| --- | --- | --- |
| 架构与设计文档 | 划分理由、命名意图 | 当前实现是否仍按此划分 |
| README | 对外入口与能力清单 | 内部边界与真实调用链 |
| 配置与启动脚本 | 组装顺序、实际存在的组件 | 组件内部职责 |

数据流向很少写在文档里，主要从调用关系里读出来。办法是对文档点名的每个关键调用查一次引用：在 IDE 里看实际被哪些位置调用、又调用了哪些函数。

对不上有两种：文档写 A 调用 B，而 B 的引用列表里没有 A；或 B 有一批调用者，文档完全没提。原因可能是文档过期、存在未记录的调用路径，也可能是引用工具没有解析到间接调用。

只有 README 时，把 README 当入口清单用：对每个对外入口查一次引用，顺调用关系看一层，得到的是边界的初步假设，仍需继续核对。文件树只给命名，不给执行关系。

文档和 README 都没有时只能自建框架。可以从四处入手：数据形状（数据库 schema、序列化格式、协议定义）、配置与启动脚本、被 import 或调用次数较多的符号、测试目录的组织。这些线索都只是入口，边界仍要回到调用关系里核对。

不必从 main 起逐行读完启动代码。启动与配置能说明组件如何组装。问题决定入口：从与问题相关的业务入口进入，比顺序遍历启动路径更省时间。

# 一次只读一条路径

路径指一个输入值从进入模块到产生一个可观察输出所经过的全部语句。一次只读一条。

起点由要回答的问题倒推：修一处失效，从现象出现的位置往回追；加一个特性，从最接近该特性的既有入口进去；弄清一个机制，从这个机制的名字最可能出现的入口进入。

下图是一张调用图，只有一条路径被点亮，编号 1 至 5 是这条路径上的五处停留点，其余节点与边淡色显示。

![760](../assets/Code-Graph-And-One-Path.svg)

五处各问一个问题：

1. 入口：这个输入从哪个公开函数进来。
2. 解析：输入在这里被变成什么内部表示；哪些字段被丢弃，哪些被补上默认值；在进入之前被哪些步骤改过。
3. 校验：什么条件下拒绝，拒绝时是抛错还是返回哨兵值。
4. 存储：改了哪些状态，这些状态之后由哪些代码读取。
5. 返回：成功与失败各返回什么，失败信息在这一段有没有被改写。

一条路径读完时，应能回答：什么输入进入哪个分支，失败返回什么，错误在哪一处被吞掉或转成别的形式。

函数名可以提示用途，但不能替代阅读：函数叫 RefreshToken，不能据此断定不访问数据库，该函数可能先查库校验、再续期、并把旧记录作废。

名字与调用次数都是线索，不是证据。多处调用且用法一致，只能说明这个名字对调用者够用；副作用是否与名字相符，仍要看定义、分支与测试。调用点用来定位读取顺序，关键行为在定义与测试里确认。

# 什么时候必须停下来

遇到不认识的库 API、语法糖、宏、关键字，优先判断相关机制是否改变控制流、所有权或生命周期、错误传播。这几类语义会改变路径方向，需要读懂；其余语义可以先记下签名与可能的失败方式，继续读。

读懂的顺序是三步：

1. 跳到定义，先看签名，再找失败分支，最后看关键分支。
2. 回到本项目找现有调用点，看传入什么、如何处理返回值与错误。
3. 结合定义、调用点与文档，核对前置条件与失败方式。

返回类型给出显式报告失败的方式。返回 Optional、Result、error 或 throws 的，失败分支要读；返回裸指针或原始值的，失败可能藏在错误码、panic 或哨兵值里。即使返回类型声明显式错误，也不排除 panic、异常或进程退出等其他失败方式，需要一并核对。

暂时弄不懂的 API，记下签名与失败方式，标成待证，之后回到这里补。

# 读懂的判据

读懂的标志是能写出一份行为陈述，格式固定四行。

```text
输入：长度为 0 的切片
经过：NewCache 在第 42 行判空，返回错误
输出：nil 与 ErrInvalidSize
证据：第 42 至 45 行；cache_test.go:88 有同类用例
```

判据是别人拿这四行去读一遍或执行一遍就能判定真假。出现“应该”“大概”“通常会”的，就不是行为陈述。

证据来源有三种，并列，不排序：

- 代码本身：失败分支与已有测试用例，能确认静态可读的行为。
- 运行时复现：用断点停在这条路径的关键分支，或写一个先失败的测试。
- 已有痕迹：线上日志、错误监控里的堆栈、issue 里的复现路径。

手上有哪一种就用哪一种，判据不因为少了某一种而放松。

有几类行为无法只靠当前函数确定：动态分派与依赖注入的调用目标、宏与代码生成、由配置或环境变量决定的分支、并发交错。遇到这类行为时，当前函数只能给出候选，需要继续查绑定、配置、生成代码或运行证据，未确认前不能当作改动依据。

# 改动

改动前先记录复现步骤与期望行为。能运行就写成测试或复现脚本；针对该问题的回归测试应在修复前失败、修复后通过。不能运行时，把行为陈述整理成可核对的清单，交给 CI 或实际运行的人，供后续判断是否修对。

改动取最小范围。读过的路径之外，每新增一处接触点，都会引入尚未验证的行为，风险随未验证范围扩大而上升。

回归优先覆盖那条路径与直接受影响的共享调用者、接口；相邻但不相关的检查不必全部重做。改动后重新取证：能运行时用运行与观察；不能运行时，用静态分支、测试或证明覆盖受影响的行为。重读补丁有帮助，但不能单独代替证据。
