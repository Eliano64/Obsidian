# 异常与中断

CPU 正常执行指令时，可能因为某个事件临时改变控制流，转去执行操作系统内核中的处理程序。这个机制常被统称为“中断机制”，分为以下两种：

- **异常**：由 CPU 内部原因产生，通常和当前正在执行的指令有关。
- **中断**：由 CPU 外部设备产生，通常和当前正在执行的指令无关。

从触发方式看，异常是**同步事件**，中断是**异步事件**，它描述的是事件和当前指令流之间的关系：

| 事件 | 与当前指令的关系 | 可预测性 | CPU 通常在何处响应 |
| --- | --- | --- | --- |
| 异常 | 由当前指令的取指、译码或执行直接引起 | 在相同机器状态下执行同一条指令，通常会在相同位置再次发生 | 当前指令执行过程中或刚完成时 |
| 中断 | 由定时器、I/O 控制器等外部部件发出，与当前指令内容无直接因果关系 | 到达时刻取决于外部事件，不能仅由当前指令推断 | 通常完成当前指令后，在指令边界检查并响应 |

例如，除零、非法指令和缺页都与正在执行的指令直接相关，属于同步异常；键盘输入、磁盘 I/O 完成和时钟信号可以在程序执行任意指令期间到达，属于异步中断。

# 中断

中断来自 CPU 外部，通常由 I/O 设备、定时器、外部控制信号等硬件因素触发。它和当前指令本身无关。 

| 类型     | 信号线  | 含义                   | 例子                |
| ------ | ---- | -------------------- | ----------------- |
| 可屏蔽中断  | INTR | 可以被 CPU 的中断屏蔽位临时禁止响应 | 普通 I/O 完成中断、定时器中断 |
| 不可屏蔽中断 | NMI  | 不能被普通屏蔽机制禁止，优先级高     | 断电                |


由于 CPU 不能对发生的中断请求立即处理，所以需要 I/O 控制器通过中断请求锁存器保存待处理状态，并向中断控制器发出中断请求。

中断控制器收到请求后将其锁存，根据屏蔽状态和响应优先级选出当前可以响应的请求，再向 CPU 发出中断请求信号。

CPU **在一条指令执行结束后**通过采样中断请求信号来检查是否有中断请求。**如果允许响应**，决定响应后，CPU 向中断控制器发出中断响应信号，中断控制器随即根据中断源产生相应的中断类型号并送给 CPU。

CPU再根据该类型号找到对应中断服务程序的入口，保存现场、转入对应的中断处理程序。

处理完成后，如果不需要终止当前任务或改由其他任务先运行，内核会恢复现场并继续被中断的执行流；若返回路径触发调度，被中断任务会在以后重新获得 CPU 时继续。

中断处理程序本身通常不能阻塞，也不能像普通进程代码那样主动等待某个条件。处理结束返回前，内核可以检查是否需要调度；如果允许更高优先级中断打断当前处理程序，则属于[[#单重中断与多重中断|多重中断]]。

## 中断隐指令

隐指令是指令系统中没有对应指令的一组操作。中断隐指令是 CPU 的 **硬件** 自动完成的一组入口操作，**不是程序员在指令系统中显式写出的指令。**

中断隐指令完成的操作依次为：

| 步骤  | 操作       | 描述                                        |
| --- | -------- | ----------------------------------------- |
| 1   | 关中断      | 将中断允许标志（IF）置 0，防止保存断点、引出处理程序期间又被新的可屏蔽中断打断 |
| 2   | 保存断点     | 保存原程序的 PC，使中断处理完成后能返回原程序                  |
| 3   | 转入内核态    | 使 CPU 从普通程序的执行状态转入内核态，执行内核代码、访问内核数据结构     |
| 4   | 引出中断服务程序 | 根据中断类型号或中断向量找到内核中的服务程序入口，并送入 PC           |



> [!important] 保存断点和保护现场不是同一件事
> | 概念 | 保存内容 | 主要由谁完成 |
> | --- | --- | --- |
> | 保存断点 | PC，即原程序下一步应从哪里继续 | 中断隐指令(硬件) |
> | 保护现场 | 通用寄存器、状态字、可能被服务程序破坏的运行环境 | 中断服务程序(软件) |


## 中断的响应与处理

中断过程分成两个阶段：

- **响应阶段**：硬件过程，CPU 响应中断，完成**中断隐指令**。它暂停现行程序，保存返回所需的断点信息，并把控制权转入内核中的中断入口。
- **处理阶段**：软件过程，操作系统内核或设备驱动执行中断服务程序。

### 中断响应判优

`IF` 是 **中断允许标志（Interrupt Flag）**，是处理器状态字中的一个标志位，也是所有**可屏蔽中断**的总开关：

- `IF=0`：CPU 不响应任何可屏蔽中断；
- `IF=1`：CPU 可以响应可屏蔽中断。

不可屏蔽中断（NMI）不受 `IF` 控制。

当 `IF=1` 且多个中断请求同时到达时，CPU 应当先响应哪一个，由**中断响应优先级**决定。

响应优先级由硬件的中断优先级排队电路确定，也可以由软件通过设置优先级寄存器等方式实现。

### 中断响应

1. 外部设备或定时器发出中断请求。
2. CPU 在指令边界检查中断允许标志和屏蔽条件；若多个请求同时到达，中断控制器或 CPU 进行判优，选出本次响应的中断源。
3. 中断控制器向 CPU 提供中断向量号。
4. CPU 执行**中断隐指令**：关闭或屏蔽新的可屏蔽中断，保存原程序下一条指令的 PC 和处理器状态，切换到内核态，并根据向量号转入内核中断入口。

### 中断处理

1. 内核公共入口保存通用寄存器等现场，再分派到具体中断服务程序。
2. 中断服务程序完成具体服务，并向设备或中断控制器确认该中断已经处理。
3. 内核恢复现场，执行中断返回指令，回到原程序下一条指令继续执行。

### 中断上下文

中断处理程序是在处理“当前 CPU 收到的硬件事件”，不是在替发起这次 I/O 的进程继续执行。因此处理时不是在该进程的上下文中，而是一个特殊的执行环境，称为**中断上下文**。

中断上下文没有一条可以由它自己阻塞、以后再从等待点继续的进程执行流。因此，中断处理程序通常不能睡眠或等待 I/O，只应完成必须立即处理的工作；耗时工作要交给之后可以被调度的内核执行机制。

系统调用通常不同。进程 A 发起系统调用后，内核仍然在 A 的**进程上下文**中执行，所以在内核允许的位置可以阻塞 A，并调度其他任务。

中断处理结束后，CPU 可以继续被打断的执行流；如果此时需要调度，也可以先运行另一个任务。这里的关系见 [[Process-Address-Space#进入内核态时，当前进程不一定改变|进入内核态时，当前进程不一定改变]]。

## 单重中断与多重中断

![1000](../assets/single-multiple-interrupt-flow.svg)

**单重中断**是在执行中断服务程序时不响应新的中断请求。它流程简单，但高优先级事件可能必须等待当前服务程序结束。

**多重中断**允许在中断服务程序中重新开中断，使更高优先级的中断源可以打断当前中断服务程序。多重中断需要处理中断优先级、屏蔽字和现场嵌套保存。

> [!note] 开中断
 中断服务程序保存好现场后，可以通过软件开中断，把 `IF` 重新置为 `1`；中断返回时再恢复进入中断前的值。
>
> **单重中断**在整个服务过程中保持关中断，最后由中断返回指令恢复中断前的 CPU 状态，其中包括中断允许标志。
>
> **多重中断**先保存当前现场和屏蔽状态，再由软件显式开中断。此后只有未被屏蔽且优先级更高的请求可以打断当前服务程序。

多重中断成立的关键条件：

- 中断服务程序中提前设置开中断。
- 高优先级中断源有权打断低优先级中断源。
- 使用屏蔽字控制哪些中断源可以继续申请。
- 每次嵌套都要保存对应现场和屏蔽字，返回时逐层恢复。

由[[#中断屏蔽机制]]实现。

### 中断屏蔽机制

多重中断中，中断服务程序保存好现场后会重新开中断。

中断屏蔽字是一组 `0/1`，每一位对应一个中断源。某位为 `1`，表示在处理期间屏蔽该中断源；为 `0`，表示其请求不被屏蔽。它决定哪些中断可以打断当前中断服务程序，因此中断屏蔽字决定了**中断处理优先级**。

中断处理时，**中断服务处理程序**保存原屏蔽字，再把预先规定好的新中断屏蔽字写入中断屏蔽寄存器。

> [!warning] 屏蔽字的常见判断
> 屏蔽字中 `1` 越多表示屏蔽范围越大。
> 每个中断源对应的屏蔽字至少要能屏蔽自身，否则可能在处理中被同源中断反复打断。

## 中断向量表（中断部分）

中断被接受后，CPU 必须立即转入对应的内核中断入口。为此，系统提前建立一张按编号索引的**中断向量表**：启动阶段准备表和公共入口，设备初始化时再建立设备 IRQ、向量号与驱动处理函数之间的关系。

| 对象        | 含义                   |
| --------- | -------------------- |
| 中断向量号 $i$ | 标识本次外部中断，也是对应向量表项的下标 |
| 向量表项      | 内容是中断向量              |
| 中断向量      | 表项给出的中断处理程序入口地址      |
| 中断服务程序    | 入口最终分派到的内核或驱动代码      |

### 启动阶段

| 参与者 | 负责的内容 |
| --- | --- |
| 处理器体系结构 | 规定向量号范围、表项格式、查表方式和表基址寄存器 |
| 固件 / BIOS | 在操作系统尚未运行时提供启动期临时表和基础处理入口 |
| 操作系统内核 | 建立最终向量表，填写默认入口和中断公共入口 |
| 中断控制器与驱动 | 建立设备 IRQ、向量号和具体驱动处理函数之间的运行时关系 |

机器刚上电时，操作系统还没有运行，但启动过程仍可能需要基本 I/O，固件会先准备启动期临时表和基础入口。

内核接管机器后，不会把固件提供的临时表直接当作最终运行环境，而是建立与自身内核代码、保护机制和驱动框架配套的表。顺序是：

1. 暂时屏蔽或严格控制外部中断，只保留启动所需的最小执行环境；
2. 准备中断公共入口和默认处理程序；
3. 分配向量表，并预先创建体系结构规定数量的表项；
4. 把处理程序入口信息和控制属性填入相应表项，未使用的表项通常指向默认处理程序或保持为不可用状态；
5. 通过专用指令把表的基址和界限装入 CPU 的向量表寄存器。

此时 CPU 已经知道最终向量表位于哪里，但外部设备中断仍保持屏蔽，要等中断控制器和驱动准备完成后再开放。

### 运行准备

最终向量表建立后，还需要把“某个设备发出请求”连接到“某个驱动函数”。以设备驱动初始化为例，过程通常是：

1. 驱动向内核申请中断资源并登记处理函数；
2. 内核为设备选择或分配向量号；
3. 内核在自己的第二级分派表中记录向量号与驱动处理函数的关系；
4. 内核配置 PIC、APIC 等中断控制器，把设备 IRQ 映射到该向量号；
5. 所有入口和映射就绪后，内核解除该中断的屏蔽。

硬件向量表的槽位通常在启动时已经按体系结构规定的数量建立。表项可能直接指向某个处理程序，也可能统一指向一组汇编入口，再由内核根据向量号进行第二次分派。共享中断还可能对应一条驱动处理链。

因此，注册新的中断类型或设备处理程序时，系统主要是在**分配向量号、更新表项或登记第二级分派关系**，并不是到这时才临时创建一个向量表槽位。

### 运行时查表

中断到达后的向量查找过程是：

1. 中断控制器向 CPU 提供外部中断向量号；
2. CPU 从专用寄存器取得向量表基址；
3. CPU 用向量号定位相应表项，读取处理程序入口和体系结构要求的控制信息。

随后 CPU 完成硬件入口操作，内核公共入口再分派到设备驱动的中断服务程序。

整体流程即：

$$
\text{向量号}\rightarrow\text{第 }i\text{ 个向量表项}
\rightarrow\text{处理程序入口信息}\rightarrow\text{中断服务程序}
$$

# 异常

异常来自 CPU 内部，可以分为三类。

| 类型  | 英文    | 含义                          | 处理后返回位置                              |
| --- | ----- | --------------------------- | ------------------------------------ |
| 故障  | fault | 指令执行过程中发现问题，但通常可以修复         | 返回引发故障的指令，重新执行；若不可恢复故障则退出当前进程（如除0故障） |
| 自陷  | trap  | 指令正常执行完毕触发，主动转入OS内核，常用于系统调用 | 返回下一条指令                              |
| 终止  | abort | 严重**硬件**错误，通常无法恢复           | 程序被迫终止                               |

故障的典型例子是缺页故障：进程访问某个逻辑地址，地址变换时发现目标页不在主存，于是转入缺页处理程序；页面调入后，原访存指令重新执行。

自陷通常是程序主动进入内核的方式。例如用户程序执行系统调用指令，请求操作系统完成文件读写、进程创建等特权操作。

终止表示严重错误。例如无法恢复的机器检查错误，操作系统通常会终止相关进程，甚至导致系统停止。

若异常处理过程中需要等待某事件，则同样进行阻塞然后进程调度。

## 异常处理


[html-card height=700 step=40](../assets/exception-handling-process.html)

一次异常处理过程是：

1. CPU 在当前指令执行过程中检测到异常。
2. CPU 确定异常类型，并找到相应异常处理入口。
3. CPU 保存必要的断点和程序状态等信息，进入内核态并转入异常处理程序。
4. 操作系统保存其他必要现场。
5. 执行具体异常处理；若当前进程需要等待某事件，使其阻塞并调度其他进程。
6. 若异常可恢复，则恢复现场，并根据异常类型重新执行原指令或从适当位置继续；若不可恢复，则终止当前进程。

> [!warning] 没有“多重异常”机制
> 
> 异常由正在执行的指令同步产生。异常处理程序自身仍可能因为执行新的指令而再次触发异常。它是处理程序中的新指令产生了新异常，内核必须处理，不能设置优先级和屏蔽。

## 中断向量表（异常部分）

异常和中断共用一张中断向量表，但两者的向量号来源不同：

- 异常向量号由处理器体系结构规定，并由 CPU 根据当前指令产生的异常直接确定；
- 外部中断向量号通常由中断控制器提供，或由内核在设备初始化时建立 IRQ 到向量号的映射。

### 启动阶段

| 参与者 | 负责的内容 |
| --- | --- |
| 处理器体系结构 | 规定异常类型、向量号、表项格式、查表方式和进入内核时必须保存的状态 |
| 固件 / BIOS | 在内核接管前提供启动期临时表和最基本的异常入口 |
| 操作系统内核 | 建立最终向量表，安装各类异常入口和默认处理程序 |

内核建立最终向量表时，先让中断保持屏蔽，再完成以下工作：

1. 先准备启动早期必须使用的最小异常入口；
2. 准备各类异常的专用入口和无法归类时使用的默认入口；
3. 按体系结构规定的数量分配向量表项；
4. 在相应表项中填写入口地址和控制属性，未使用的表项指向默认处理程序或标为不可用；
5. 通过专用指令把表的基址和界限装入 CPU 的向量表寄存器。

最终向量表尚未完全建立时，除零、非法指令、缺页等异常仍可能发生，所以启动早期必须先准备最小异常入口。最终表建立后，内核是在已有表项中安装具体入口或更新第二级分派关系，并不是等异常第一次出现时才创建表项。

### 运行时查表

异常发生后的向量查找过程是：

1. CPU 根据异常原因在内部得到异常向量号；
2. CPU 从专用寄存器取得向量表基址；
3. CPU 用向量号定位表项，读取异常入口和体系结构要求的控制信息；
4. CPU 保存规定的返回信息并转入内核态；
5. 内核公共入口再分派到具体异常处理程序。

$$
\text{异常原因}\rightarrow\text{异常向量号}
\rightarrow\text{第 }i\text{ 个向量表项}
\rightarrow\text{异常处理程序}
$$

# CPU 响应顺序

当前指令引起异常时，CPU 必须先确定这条指令的结果。在当前指令的结果确定以前，CPU 不会去响应普通可屏蔽中断。

不可屏蔽中断用于电源掉电等必须尽快处理的严重硬件事件。这类紧急硬件事件处理先于异常处理，异常处理又先于普通可屏蔽外部中断的处理。
